# Nothing Phone (1) WLAN Graceful Failure

Экспериментальный Magisk-модуль для моего Nothing Phone (1), который пытается
не допустить полной перезагрузки Android после аппаратного сбоя Wi‑Fi/WPSS.
Если радиомодуль уже не восстановить, моя цель проще: оставить Android и
Bluetooth работающими, показать уведомление, сохранить один архив с логами и
дать мне самому выбрать момент для перезагрузки.

> [!CAUTION]
> Это не ремонт платы и не универсальный твик. Модуль рассчитан только на
> Nothing Phone (1) (`Spacewar`), сборку `2509261631`, ядро
> `5.4.274-qgki-g4670d6bdb795` и известные точные бинарники драйвера. У телефона
> почти наверняка есть аппаратная неисправность. Удары по телефону опасны для
> платы и аккумулятора и могут сделать повреждение необратимым.

## Как всё началось

Мой телефон начал внезапно зависать: останавливалась музыка, экран переставал
реагировать, затем появлялся Nothing CrashDump и телефон перезагружался. Иногда
Android запускался с первого раза, но иногда устройство часами снова показывало
ошибку. Самый тревожный признак — после удара о твёрдую поверхность оно порой
внезапно начинало загружаться. Это похоже на плохой контакт, повреждённую пайку,
питание или сам радиомодуль, а не на обычную ошибку приложения.

Сначала компьютера под рукой не было. Я собирал данные прямо в Termux с root от
Magisk: `bootreason`, `pstore`/`ramoops`, `dmesg`, `logcat`, tombstones и vendor
ramdump. Причина загрузки повторялась как:

```text
kernel_panic,bug
```

В журналах постоянно встречались:

```text
MHI_DEV_SYS_ERR
Driver reinit failed
WLAN Panic
reset_reason: subsys-restart: Resetting the Soc - wpss crashed
```

То есть первым ломался WPSS/WLAN, а затем код восстановления превращал отказ
одной подсистемы в падение всего ядра.

## Как нашли первый драйвер

Первой обнаружилась копия:

```text
/vendor/lib/modules/qca_cld3_wlan.ko
```

В v0.2 я изменил возврат из `wlan_hdd_pld_reinit()`: после уже обработанного
неудачного восстановления драйвер сообщал ICNSS об обработанном callback, чтобы
она не запускала ещё одну опасную попытку. Телефон стал чаще загружаться сразу,
но перезагрузки не исчезли.

В v0.3 добавилась проверка состояния драйвера. Реальные crash-логи показали,
что одного флага недостаточно: повторный callback мог всё равно попасть в
`osif_psoc_sync_trans_resume()` после закрытия транзакции и вызвать kernel BUG.

## Как нашли второй драйвер

После очередного падения хеш первой копии был правильным, но стек выглядел так,
словно работает штатный код. Поиск показал вторую копию:

```text
/vendor/lib/modules/5.4-gki/qca_cld3_wlan.ko
```

А в `init.target.rc` нашлись две параллельные команды `modprobe`: одна загружала
драйвер из `/vendor/lib/modules`, другая — из `/vendor/lib/modules/5.4-gki`.
Возникала гонка: при одной загрузке побеждала изменённая копия, при другой —
штатная. Поэтому v0.4 стала собирать и проверять два разных `.ko` с разными
смещениями и ELF-релокациями.

## Почему потребовались v0.7 и v0.8

Новые `pstore` показали ещё два независимых пути паники:

1. Даже первая автоматическая реинициализация могла упасть внутри
   `osif_psoc_sync_trans_resume()`. В аварийной v0.7 callback сразу направлен в
   существующий обработанный выход. После отказа WPSS Wi‑Fi остаётся недоступен
   до ручной перезагрузки, зато Android не должен повторно входить в уже
   завершённую транзакцию.
2. В `__hdd_soc_probe()` после третьего последовательного провала код намеренно
   вызывал `__qdf_bug()`. v0.8 перенаправляет только условный переход мимо блока
   assert в уже существующую штатную ветку очистки.

v0.9 сохраняет обе эти модификации. Полные фирменные WLAN-бинарники в репозиторий
не включены: установщик копирует активные файлы с телефона, принимает только
заранее известные SHA‑256, меняет точные байты и проверяет итоговые SHA‑256.

## Почему понадобился ранний WPSS guard

Часть CrashDump происходила раньше, чем обычный `service.sh` Magisk успевал
запуститься. В sysfs у WPSS было:

```text
/sys/bus/msm_subsys/devices/subsys4/name          = wpss
/sys/bus/msm_subsys/devices/subsys4/restart_level = SYSTEM
```

При `SYSTEM` авария WPSS могла потребовать сброс всего SoC. В проверенном
boot-образе политика как можно раньше меняется на `RELATED`, то есть сбой
остаётся ограничен связанной подсистемой. Bluetooth на моём устройстве при этом
продолжал работать.

Важно: это не пересборка исходного кода ядра. Это пересборка **boot-образа** с
двумя небольшими файлами Magisk `overlay.d`: init `.rc` и shell-guard. Само ядро
внутри boot не заменяется. v0.9 дополнительно повторяет установку `RELATED` в
`post-fs-data.sh`, но это более поздняя страховка, а не замена раннему guard.

## Что делает v0.9

- на устройстве создаёт и проверяет обе модифицированные копии WLAN-драйвера;
- блокирует небезопасный автоматический WLAN reinit после сбоя WPSS;
- обходит deliberate BUG после трёх провалов probe, используя штатную очистку;
- выставляет для WPSS `restart_level=RELATED` в `post-fs-data`;
- не выключает переключатель Wi‑Fi в Android и не заменяет Bluetooth-драйверы;
- показывает русские или английские сообщения по системному языку;
- хранит ограниченные по размеру логи и по Action создаёт один `.tar.gz`;
- по отдельному пункту Action снимает полный backup `boot_a`, внедряет ранний
  guard только в копию и сохраняет патченый `.img` в `Download`;
- никогда автоматически не прошивает `boot_a` или другой раздел.

## Установка

Через Magisk: **Модули → Установить из хранилища → выбрать ZIP →
перезагрузить телефон**.

Через Termux:

```sh
su -c 'magisk --install-module /sdcard/Download/Nothing-Phone-1-WLAN-Graceful-Failure-v0.9.zip'
```

После первой загрузки ожидаются хеши:

```sh
su -c '
sha256sum /vendor/lib/modules/qca_cld3_wlan.ko
sha256sum /vendor/lib/modules/5.4-gki/qca_cld3_wlan.ko
cat /sys/bus/msm_subsys/devices/subsys4/restart_level
'
```

```text
27a2bc077b38299f495377b1b13ed9143bfc53e48904d89af080834a1801d47c
8d76c32c557648c7633b8d6090dcc8a0afb4d6dcb15b027338e244d1f7156166
RELATED
```

## Меню Action по кнопкам громкости

Первый экран:

- **Громкость +** — показать uptime;
- **Громкость −** — дополнительные действия.

Второй экран:

- **Громкость +** — создать один архив диагностики;
- **Громкость −** — создать backup `boot_a` и отдельную патченую копию.

Если Action не может прочитать кнопки, boot-builder не запускается: создаётся
только безопасный диагностический архив.

## Создание boot-образа через Action

Перед началом скрипт повторно проверяет модель, сборку, слот `_a`, размер и
SHA‑256 раздела, наличие Magisk ramdisk и не менее 700 МБ свободного места.
Файлы получают полные дату и время, например:

```text
/sdcard/Download/Nothing-Phone-1_boot-a_BACKUP_2026-10-01_21-30-05.img
/sdcard/Download/Nothing-Phone-1_boot-a_WPSS-RELATED_PATCHED_2026-10-01_21-30-05.img
```

Скрипт читает `/dev/block/by-name/boot_a`, но нигде не открывает его для записи.
`magiskboot` работает только с временной копией. В ramdisk через `overlay.d`
добавляются:

```text
overlay.d/wpss_related_rescue.rc
overlay.d/sbin/wpss_related_rescue.sh
```

Затем оба файла извлекаются обратно и сравниваются с исходными. Только после
проверки новый образ попадает в `Download`. Команда `add` идемпотентна: если
ранний guard уже есть, запись заменяется тем же проверенным содержимым.

## Как проверять патченую копию

Сначала скопировать патченый `.img` на ПК и выполнить из fastboot:

```bat
fastboot.exe boot Nothing-Phone-1_boot-a_WPSS-RELATED_PATCHED_YYYY-MM-DD_HH-MM-SS.img
```

Это временная проверка. Не использовать `fastboot flash`, пока образ не
загрузился, Magisk не работает, WPSS показывает `RELATED`, а Wi‑Fi/Bluetooth и
обычная перезагрузка не проверены. Полный backup с той же датой нужно сохранить
на ПК отдельно.

## Диагностический архив

Action сохраняет один файл вида:

```text
/sdcard/log/wlan_graceful_fail/wlan_dump_YYYY-MM-DD_HH-MM-SS.tar.gz
```

Внутри находятся статус модуля, uptime, boot reason, текущая WPSS policy,
SHA‑256 драйверов, `pstore`, хвост `dmesg`, kernel log и журнал раннего guard.

## Аварийное отключение

В терминале OrangeFox:

```sh
touch /data/adb/modules/wlan_graceful_fail_spacewar/disable
```

После перезагрузки Magisk перестанет подменять WLAN-драйверы. Модуль не изменяет
раздел `vendor` напрямую. Ранее самостоятельно прошитый boot-образ отключением
модуля не откатывается — для него нужен сохранённый backup.

## Ограничения

Модуль не может исправить физический контакт, питание, PCIe/MHI, память или сам
радиочип. Он не гарантирует защиту от другого kernel panic, зависания всего SoC,
повреждения файловой системы или отказа до момента, когда ранний init успеет
применить guard. Wi‑Fi после сбоя может исчезнуть до следующей ручной
перезагрузки. Это контролируемый аварийный режим, а не штатное восстановление.

## English summary

This exact-build Magisk module is a containment experiment for a physically
unstable Nothing Phone (1). It patches both competing `qca_cld3_wlan.ko`
locations on-device, blocks unsafe automatic WLAN reinitialization, skips a
known deliberate BUG after repeated probe failures, sets WPSS restart policy
to `RELATED`, records bounded logs, and offers a bilingual volume-key Action
menu. The third Action builds a complete timestamped `boot_a` backup and a
separate early-init patched image in `Download`; it never flashes the image.
Only Spacewar build `2509261631` and the exact documented hashes are accepted.
